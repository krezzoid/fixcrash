## Testbed scenarios (Android, step 1)

1. **Parser:** a `!!` or NPE on an optional JSON field that the backend started to omit. Reproducible with a JVM unit test.
2. **Paging:** an `IndexOutOfBoundsException` at a page boundary. Reproducible with a JVM unit test.
3. **Lifecycle:** `IllegalStateException: Fragment not attached to a context`, from a callback after the user leaves the screen. **Not** reproducible by a JVM unit test. The expected outcome is an honest report and no PR. Risk: Robolectric with `FragmentScenario` and a paused main looper can probably reproduce it. Step 4 decides whether the agent may add Robolectric to a project that doesn't have it. If it may, `verify` has to apply that build-file change at the crashing commit too: today it overlays test sources only. In the first eval run the reproducer took another way: it built the fragment with `Unsafe.allocateInstance` and called the private callback by reflection, which passed the "same failure" check. `reproduce` and `verify` now refuse such shortcuts (`RESEARCH.md` §7).

The app, triggers and setup: `testbed/android/README.md`.

### SwiftUI (5.7)

fixcrash's iOS path doesn't depend on UIKit: events, the crash site from the release build (ADR-0002), the runner and the crash log check work on machine code and test results. What SwiftUI changes is where app code crashes and how a test gets there: inside a view's `body`, in an action closure SwiftUI calls, after an `await` in a `.task`. The UIKit testbed covers none of these.

The SwiftUI testbed is an app of its own, `testbed/swiftui`: the SwiftUI `App` lifecycle, Firebase set up through `@UIApplicationDelegateAdaptor` as Firebase documents for SwiftUI, Crashlytics through SPM, a hosted unit test target, no UI test target (as the UIKit testbed). It has its own bundle id and Firebase app, so its crashes don't mix with the UIKit testbed's on the simulator or in Crashlytics.

## React Native (step 6)

JS errors only. A native crash in an RN app is an Android or iOS crash, and goes down those paths (`--project-dir android` or `ios`).

What is new compared with the native paths (`RESEARCH.md` §7, 2026-10-16):

- A fatal JS error reaches Crashlytics as a native crash: `com.facebook.react.common.JavascriptException` on Android, `RCTFatalException` on iOS. Its message holds the JS error's type, Hermes's message and the JS stack as `<function>@1:<column>` lines (6.3).
  - On Android every fatal JS error lands in one issue, blamed on `ExceptionsManagerModule.reportException`. An issue says nothing about which crash it is; only its events do.
  - React Native Firebase's own report of a fatal error, `JavaScriptError` with frames, is lost: the app exits before it is written. The one exception is iOS with handler chaining on, where it arrives as an extra non-fatal (6.3).
- A non-fatal one, from `recordError`, is React Native Firebase's `JavaScriptError`. It carries the message but not the type, and frames like `?anon_0_ (address at index.android.bundle:1:698961)`. After an `await`, the function's name is gone.
- With Hermes, a position points into the compiled bytecode. Only the crashing commit's source map (Metro's map composed with the Hermes compiler's) turns it into a file, a line and a function. Crashlytics doesn't do this. An Android release build leaves that map in its build directory, and an iOS build makes none by default.
- Jest runs tests on Node, not on Hermes. The same bug throws with a different message, and a crash caused by an engine difference doesn't reproduce at all.
- The tests need `node_modules` at the crashing commit, in fixcrash's worktree.

The testbed is a bare React Native app from the Community CLI template (Jest and react-test-renderer included, Hermes, the New Architecture), not an Expo app. React Native Firebase documents the template first, and Expo changes the commands, not the problem (deferred list). One app covers both platforms: Android first, then iOS to check that its events have the same shape.

## Publish (step 7)

fixcrash goes public in three places: a public repository that is its own marketplace, a website, and Anthropic's plugin directory. What publishing involves (`RESEARCH.md` §7, 2026-10-17):

- **Our own marketplace.** A pushed `.claude-plugin/marketplace.json` in a public repository is the whole publication. Users run `claude plugin install fixcrash --marketplace krezzoid/fixcrash` (Claude Code 2.1.292 or later), or `claude plugin marketplace add krezzoid/fixcrash`, then `claude plugin install fixcrash@fixcrash`.
  - Users get an update only when `version` in `plugin.json` changes. Auto-update is off for third-party marketplaces unless the user turns it on.
- **What an install gets.** Claude Code copies the plugin folder into its cache. Before 7.1 that folder was the repository root, so an install carried the testbeds, docs and tests, and the root `package.json` with `package-lock.json` made Claude Code install the dev dependencies into it. Since 7.1 the plugin is in `plugin/` (ADR-0006): 29 files, no package install.
- **Anthropic's directory.** Submission is from the developer portal (claude.ai/directory/manage) and needs a paid claude.ai plan.
  - **Blocking:** no LICENSE, a README under 40 words, an unpinned `npx`.
  - **Held for a reviewer:**
    - binary files: `gradle-wrapper.jar`, a keystore; images are fine;
    - files over 256 KiB, such as the RN testbed's lockfile;
    - a lockfile install;
    - a pinned `npx` package, which is how our Firebase MCP server starts.
  - **The security scan:** wants the README to say everything the plugin runs, sends and fetches.
  - **The top-level `bin/`:** keeps the plugin out of claude.ai chat and Cowork. It loads in Claude Code, the only place fixcrash can work.
- **The website**, https://fixcrash.app, is a Next.js app exported as static files (`output: 'export'`, no server), in a repository of its own (`krezzoid/fixcrash-site`), built by Cloudflare Pages' Git integration. Cloudflare Pages builds from a private repository too.

## Deferred

- Crash-pattern memory: faster on the second similar crash.
- Sentry as a second crash source (Sentry MCP); the issue → event → stack shape is the same.
- Headless runs in CI (`claude -p`) on new top issues.
- Real network isolation for test runs, beyond `--offline`.
- Measure the unit-reproducible share on a real production app's top crashes. This needs access to one.
- From step 3:
  - `--base` is the agent's word. `verify` could check it against the build stamp revision recorded from the event, when there is one.
  - The hook spots state writes and PR commands by their text. A command that builds the path or the command in a variable gets past it; so does a pull request opened on the web after `git push`. The threat is a careless agent, not a hostile one.
  - The reproducer's Bash can still edit app code (`sed -i`); only Write and Edit are held to test files.
  - The guard turns on per repository, for sessions that read crash events and for `fixcrash/` branches. A PR from another branch in a later session isn't checked.
  - A Robolectric test counts as a JVM test, but adding Robolectric to a module is a build change, which `reproduce` and `verify` don't apply at the crashing commit (see the lifecycle scenario).
- From step 4:
  - Robolectric in a module that doesn't have it: for now the report carries the setup as a build-file diff. Revisit after the first real app; the options and the design for applying it with the user's consent are in `docs/adr/0001-test-libraries-the-module-lacks.md`.
  - The reproducer may answer NOT REPRODUCED without a single `fixcrash reproduce` run. Fine with a concrete reason, as in the lifecycle run, but a lazy answer looks the same. Requiring one run would put tool output in every report.
  - `claude plugin eval` (`RESEARCH.md` §9, question 7) wasn't tried: the eval ran by hand, measured with `eval/metrics.ts`.
  - The shortcut check (`plugin/src/shortcut.ts`) reads the new lines of the changed test files. A mock of the class under test (Mockito and MockK build it without its constructor) is caught by the reproducer's rules only, not in code. A shortcut in a helper outside the changed test files, or written another way, gets past it.
- From step 5.4: a test target that isn't folder-synchronized lists its files in `project.pbxproj`, so a new test file isn't built at the crashing commit. The reproducer can add its test to an existing test file instead; decide with the first real app that has such a target.
- From step 5.5:
  - `xcodebuild test-without-building` hung after a crashing test about half the time, collecting diagnostics: fixcrash passes `-collect-test-diagnostics never` since step 5.6, and keeps a 2-minute timeout and one retry in case.
  - The Release build of the crashing commit runs the app's Release build phases: the testbed's uploads a dSYM to Crashlytics. A switch to turn such phases off would need the app's cooperation.
  - Swift packages are resolved into fixcrash's own DerivedData: the first run needs the network.
  - A crash in a framework the app embeds, an `NSException`, and device builds' crash sites are untried (ADR-0002).
- From step 5.7.3: after Xcode updates itself, the system's CoreSimulator can be older than the new Xcode needs until its components are installed (an admin password). `xcodebuild` then says only "Unable to find a device matching the provided destination specifier", with the cause a few lines above it, and `simctl` hangs. The runner's hint could point at the cause.
- From step 6:
  - Expo apps: the `jest-expo` preset, the bundle from `expo export:embed`, native directories generated by prebuild. The step 6 testbed is a bare RN app.
  - A native crash in an RN app's own native module goes down the Gradle or Xcode path with `--project-dir android` or `ios`. Untried in step 6. On Android its event has no build stamp, because the Gradle root isn't the git root, so only tags find the commit.
  - React Native Firebase 26.4.0 loses its own report of a fatal JS error: `crashWithStackPromise` exits before the SDK writes it (`RESEARCH.md` §7, step 6.3). Worth an issue upstream, with the logcat lines; Ilya decides.
  - Why the iOS render crashes didn't reach Crashlytics (an `RCTFatalException` thrown during render, `.ips` written). Parser and engine `RCTFatalException`s did.
  - Yarn and pnpm apps: `reproduce`, `verify` and `symbolicate` stop with a message (ADR-0005).
  - Apps with Hermes off: their bundle is plain minified JS, with no `hermesc` step and other positions. Untried.
  - fixcrash leaves a JS project's worktree, with its `node_modules` (hundreds of MB), in the user's cache directory. No command removes it yet; deleting it by hand is safe.
  - One JS bug on both platforms is two issues and, with two sessions, two pull requests (`EVAL.md`, React Native, finding 4). Matching JS errors across an app's Android and iOS ids by their symbolicated file and line would join them.
  - An event from an earlier build with the same version number has other bundle offsets, and the tagged commit's map places it wrong (`EVAL.md`, React Native, finding 2). Nothing flags it; the agent noticed by the message.
  - The same JS error type at the same line can come from an input the app never gets (`EVAL.md`, React Native, finding 3). Only the reproducer's judgment rules it out, as with the native frame rule. The testbed's engine scenario could tighten its year check the next time crashes are reported.
- From step 2: the Gradle unit test task is fixed to `testDebugUnitTest`. Flavored apps need `test<Flavor>DebugUnitTest`, and plain JVM modules (task `test`) are left out of the suite. Make it configurable when a real app needs it.
